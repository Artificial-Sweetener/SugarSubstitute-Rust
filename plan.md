# Workflow output canvas: chronological work ledger

## What the output canvas is

The output canvas is the workflow's image inspection workspace. It displays live generation previews and completed images, lets the user move between output sources and batch items, and keeps the same region in view while comparing results. It belongs to the whole workflow: ordinary Comfy nodes, nested subgraphs, and SugarCube output bindings all contribute images.

In classical PySide SugarSubstitute, Output is a read-only CuteCanvas document with floating navigation chrome. The screenshot supplied for this investigation shows a large image on the right, with source tabs such as Text To Image, Diffusion Upscale, and Face Detailer along its bottom edge. Source selection, batch selection, scene overview, Auto/Manual focus, and comparison are coordinated with workflow state. Image inspection is independent of editing. The browser version will occupy the **left** of the workspace, as requested, while masonry controls or the graph occupy the remaining space.

Classical Substitute supports an A/B reveal comparison: two independently selected outputs share an image surface, with a draggable vertical or horizontal split. Its navigation preserves a selected batch position when changing sources rather than silently substituting another batch item. Auto follows arriving previews; Manual keeps the user's selected source. Its detail inspection groups link related outputs within the same workflow, scene, and batch, including when the user switches between images in a single viewer. These are useful product behaviors to carry forward, rather than treating the canvas as an enlarged node thumbnail. See [OutputCanvas](E:/devprojects/sugarsubstitute/substitute/presentation/canvas/output/output_canvas_view.py), [comparison presenter](E:/devprojects/sugarsubstitute/substitute/presentation/canvas/output/output_compare_presenter.py), [navigation policy](E:/devprojects/sugarsubstitute/substitute/presentation/canvas/output/output_canvas_navigation_policy.py), [preview navigation](E:/devprojects/sugarsubstitute/substitute/presentation/canvas/output/output_preview_navigation_presenter.py), and [detail inspection groups](E:/devprojects/sugarsubstitute/substitute/application/workflows/output_detail_inspection.py).

QPane/CuteCanvas provides the interaction model. Zoom is anchored to the image point beneath the pointer. Wheel input uses a 1.25 increase and reciprocal 0.8 decrease per traditional wheel step. A step crossing Fit or native scale lands exactly on that target; native scale wins when a step crosses both. Starting on a target allows the next step to leave it. Double click changes Fit to pointer-anchored 1:1, and changes other zoom states to centered Fit. Native 1:1 means one source pixel per physical display pixel, including display scaling. Linked inspection stores a normalized image center and magnification, rather than copying unrelated pixel offsets between images of different dimensions. See [PanZoomTool](E:/devprojects/CuteCanvas/packages/qpane/src/qpane/interaction/navigation_tool.py), [viewport](E:/devprojects/CuteCanvas/packages/qpane/src/qpane/rendering/viewport.py), [inspection projection](E:/devprojects/CuteCanvas/packages/qpane/src/qpane/inspection/projection.py), and [inspection store](E:/devprojects/CuteCanvas/packages/qpane/src/qpane/inspection/store.py).

The artificialsweetener.ai viewer implements those ideas over OSD with its own camera, constraints, input routing, and resize policy. Mouse panning is direct, without release inertia. Anchored transitions preserve the image point throughout the transition, and returning to Fit settles at the exact centered camera. Wheel handling is engagement-aware, keyboard controls are scoped to the viewer, and touch uses a shared camera for centroid-anchored pinch and pan. Rapid wheel bursts shorten or eliminate smoothing. The website also distinguishes Fit, 1:1, and custom zoom in its status display. See [interaction model](E:/devprojects/artificialsweetener.ai/frontend/design/image-viewer/osd-interaction-model.ts), [input camera](E:/devprojects/artificialsweetener.ai/frontend/design/image-viewer/osd-input-camera.ts), [mouse controls](E:/devprojects/artificialsweetener.ai/frontend/design/image-viewer/osd-mouse-controls.ts), [camera constraints](E:/devprojects/artificialsweetener.ai/frontend/design/image-viewer/osd-viewport-motion.ts), and [resize controller](E:/devprojects/artificialsweetener.ai/frontend/design/image-viewer/osd-resize-controller.ts).

There are deliberate differences between the references. QPane's Fit can enlarge a small image; the website caps Fit at native scale. QPane's default maximum is 10 times native scale, while the inspected website configuration uses 2 times native scale. The browser output canvas will use **Fit without enlargement and a maximum of 10 times native scale**. It will carry the navigation semantics, not the website's OSD tile cache, renderer configuration, or tile preparation infrastructure.

This is a production browser viewer built with Vue and ordinary image elements. It provides a useful stand-in for the native Rust canvas through reliable inspection, comparison, and workflow coordination. Its initial scope does not include painting, masks, layers, image transformations, OSD, tile workers, a server pyramid service, or a port of CuteCanvas's document engine. Comfy's image editing canvas can remain a separate destination for future editing actions; that integration is not a prerequisite for output inspection.

The reusable product is a canvas session, its views, and SugarCubes' Vue controls. The browser image surface is one presentation of a view. In Substitute, the intended composition places the complete ComfyUI/SugarCubes WebView above native canvas rendering, with transparent regions exposing the canvas. The same tabs, batch selectors, comparison controls, status, menus, and toolbars can sit over either surface. A future transparent graph backdrop can also expose the native canvas beneath the node graph; that overlap needs explicit input ownership. The browser's initial left-panel layout does not fix the native surface's lifetime or layering.

A canvas session belongs to a workflow's results and can outlive any particular presentation. A canvas view owns selection, Auto/Manual, inspection, and comparison state; its identity is independent of the window or rendering surface hosting it. Detaching moves that same view to a second window. Opening an additional view creates a new view identity with independent state unless explicitly linked. Each detached window can host a native surface and a small SugarCubes overlay entry using the shared Vue components. The main window continues to run the full Comfy frontend; the detached canvas consumes host-published state through a typed port.

This ledger implements the browser viewer, reusable overlay components, and contracts/tests needed for native attachment and multiple windows. Real native canvas attachment, graph-over-canvas presentation, and detached-window lifecycle are subsequent Substitute milestones. Their composition qualification is specified early below; this planning change does not implement those desktop features.

- [Substitute's ownership rules](E:/devprojects/sugarsubstitute-rust/AGENTS.md) assign canvas controls and desktop presentation to SugarCubes, window/document/workflow coordination to Substitute, and rendering/editing to CuteCanvas. The official [extension development guide](https://github.com/Comfy-Org/ComfyUI_frontend/blob/main/docs/extensions/development.md) describes production shims for script exports, not general access to every internal store. The [hook documentation](https://docs.comfy.org/custom-nodes/js/javascript_hooks) also advises using official hooks where available. The plan therefore keeps normal lifecycle work on public hooks and confines the necessary prompt-construction observation to one tested, reversible host adapter.

WebView2's [visual hosting model](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/windowed-vs-visual-hosting) supports host-controlled composition and requires the application to coordinate spatial input and scaling. This is the intended Windows boundary for overlapping native rendering and web UI. Actual support must be qualified against Substitute's WebView adapter; a transparent CSS background or a high `z-index` is insufficient proof of native composition or input routing.

The first release includes single-image inspection, source and batch navigation, an output overview, linked inspection across source switches, and vertical/horizontal A/B wipe comparison. The wipe is the initial simultaneous comparison mode; a second side-by-side layout is outside this ledger. Users can toggle the viewer in graph mode with either Nodes renderer. Masonry uses the same viewer when Nodes 2.0 is available. Appearance follows SugarCubes' Fluent or host appearance setting; viewer availability does not depend on Fluent being enabled or on the Rust host being present.

All choices below are resolved implementation decisions. The ledger is ordered by dependency and intended execution. Checked items record verified progress; unchecked items describe remaining work.

The following observed host behavior must shape implementation:

1. The root graph is reused across workflow tabs. Neither its object identity nor a node ID alone identifies a workflow.
2. Comfy captures the queued workflow before awaiting `graphToPrompt`, then calls `api.queuePrompt` with its returned object. Looking up the active tab only when the HTTP response arrives is too late.
3. `promptQueued` does not supply the accepted `prompt_id`; the actual queue response does. A preview or executed event can arrive before that response is processed.
4. Enhanced preview events provide a Blob, job ID, and node/display identity. Legacy Blob previews lack that complete context. Enhanced and legacy events can describe the same preview.
5. Comfy owns and releases its shared preview object URLs. A copied URL string does not transfer ownership or extend its lifetime.
6. `afterConfigureGraph` can run before the workflow store commits its new active workflow. Configuration completion alone does not authorize attaching graph results to whichever workflow is currently exposed.
